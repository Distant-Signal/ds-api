# Restoring old legs' train detail from the cold archive

`scripts/restore-leg-snapshots-from-archive.py` (DS-638) gives a tracked
train leg back its train uid and timetable when its `trains` row was pruned
before the hourly sweep (`crates/api/src/data/leg_outcomes.rs`, DS-643)
started copying them onto the leg. The only copy of such a train is the
cold archive: zstd JSONL of `trains` rows at
`<prefix>/trains/service_date=YYYY-MM-DD/part-*.jsonl.zst`.

It writes SQL for someone else to apply. It never writes to the database or
the archive, and it prints counts only (opaque public ids with `--verbose`).

## What it writes

For each matched leg, the same version 1 document the sweep writes
(`LegSnapshot`, `crates/api/src/data/leg_snapshot.rs`) with `source`
`"archive"`, and `final_train_uid` = its `trainUid`, `final_snapshot_at` =
`now()`. A leg whose `final_recorded_at` is set also gets
`finalArrivalDelayMinutes` and `trainCancelled` from the leg, and its
`final_snapshot_at` is made later than `final_recorded_at` (otherwise the
sweep would see a snapshot older than the outcome). A golden document
(`scripts/tests/fixtures/leg-snapshot-archive.golden.json`) is generated by
the script's tests and parsed by a Rust test, so the two cannot drift.

Each statement is guarded, so applying a file twice, or after the world
changed, writes nothing it should not:

```sql
UPDATE journey_legs AS jl SET ... FROM train_subscriptions AS ts
WHERE jl.id = <id> AND jl.kind = 'train' AND jl.final_snapshot IS NULL
  AND jl.train_subscription_id = <sub> AND ts.id = <sub>
  AND ts.trains_id IS NULL                      -- the train is still gone
  AND jl.final_recorded_at IS [NOT] NULL;       -- the outcome is as read
```

## Which legs, and how they are matched

Candidates: `journey_legs.kind = 'train'` whose `train_subscriptions` row has
`trains_id IS NULL` and `resolution_status` `resolved` or `schedule_matched`
(it was matched, so a missing row means pruned). Legs that already have a
`final_snapshot` are counted and skipped. The journey's retention
(`past_travel_days`) needs no filter: a leg that still exists is within it.

Once the train row is gone the subscription keeps only its pin, so that is
what is matched on:

| field | from |
|---|---|
| service date | `journey_legs.service_date` (must equal `train_subscriptions.service_date`, else mismatch) |
| origin | `pin_origin_crs`, else the leg's `origin_crs` |
| departure | `pin_scheduled_departure`, an instant |
| destination | `pin_destination_crs`, else the leg's `destination_crs` |

An archived row is a candidate when it departs that origin at that instant:
its own `origin_crs` and `scheduled_departure`, or, when the TIPLOC map is
supplied, a calling point whose TIPLOC maps to that CRS and whose
`bookedDeparture` or `publicDeparture` (London time plus `dayOffset`) is that
instant. The second form exists because a pin made at an intermediate
station carries that station and time, not the train's own ends. The row
must also reach the destination: its own `destination_crs`, or (with the
map) a later calling point. Then:

* exactly one row: matched;
* none: unrecoverable, split into older than the earliest archived service
  date, newer than the latest, and within the range but no row;
* more than one: ambiguous, skipped;
* rows found but none reaches the destination (or the service dates
  disagree): mismatch, skipped;
* no pin departure or origin: unrecoverable, no key;
* a matched row with no calling points (and no recorded outcome), or text
  `jsonb` rejects (U+0000): unusable, skipped.

Weaknesses: two different trains with the same origin and instant and a
destination both reach are ambiguous (skipped, never guessed); a leg with no
recorded destination matches on origin and time alone (reported as
"matched with no destination recorded to check"); without the TIPLOC map
only trains that start at the pin and end at the destination can match; the
calling-point form compares clock times at second precision and takes the
first reading at the autumn clock change; the archive's `trains` row is what
the train was at pruning, not necessarily at pin time.

Memory is bounded by the candidates: the archive is listed in full (to know
its range) but only the service dates that hold a candidate are read, and
only rows that depart a candidate's origin at its instant are kept. A row
not kept cannot make any candidate ambiguous.

## Running it

1. Dry run from a dump (the SQL is read-only; `umask 077`, the dump names legs):

   ```sh
   uv run scripts/restore-leg-snapshots-from-archive.py dump-sql --query candidates > candidates.sql
   uv run scripts/restore-leg-snapshots-from-archive.py dump-sql --query tiploc > tiploc.sql
   # in the production Postgres, read-only:
   kubectl ... exec -i POD -- psql -X -At -v ON_ERROR_STOP=1 -c 'SET default_transaction_read_only = on' -f - < candidates.sql > candidates.jsonl
   kubectl ... exec -i POD -- psql -X -At -f - < tiploc.sql > tiploc.jsonl
   uv run scripts/restore-leg-snapshots-from-archive.py restore \
       --candidates candidates.jsonl --tiploc-map tiploc.jsonl
   ```

2. Or let the script read the database itself (`SET default_transaction_read_only
   = on; BEGIN READ ONLY`, through `kubectl exec ... psql`):

   ```sh
   uv run scripts/restore-leg-snapshots-from-archive.py restore \
       --kubectl-context CTX --namespace NS --pg-pod POD --pg-user U --pg-db DB
   ```

The archive is read from S3 with the credentials the aggregator Deployment
names (read into memory from its `secretKeyRef`, passed to curl on stdin,
never printed), over the tailnet proxy (`--proxy`); `--archive-dir DIR` reads a
local mirror instead.

Output (counts only):

```

read: 41 service dates, 9,876 rows scanned, 0 unreadable lines
tiploc map: yes
candidates: 321
  matched: ...
  ambiguous: ...
  mismatched: ...
  unrecoverable, older than the earliest archived service date: ...
  unrecoverable, newer than the latest archived service date: ...
  unrecoverable, within the archive range but no row: ...
  unrecoverable, no recorded origin or departure to match on: ...
  unusable archived row (...): ...
  already snapshotted: ...
  (matched with no destination recorded to check: ...)
  total accounted: 321
dry run: nothing written (add --emit-sql DIR to write the SQL)
```

Then, when the counts look right, add `--emit-sql DIR` (and `--batch-size`,
default 200). It writes `batch-NNNN.sql` (one transaction per batch),
`verify.sql` (read-only: `restored` must equal `expected`, the other two
columns 0), `rollback.sql` and `manifest.json` (counts, sizes, SHA-256s; no
leg ids), all mode 0600. Roughly 4 to 7 KB per leg (the calling points are
almost all of it), so about 1 MB per 200-leg batch.

Applying: `psql -v ON_ERROR_STOP=1 -f batch-0001.sql` per file, in order, as a
role that can update `journey_legs` (the api's), then `verify.sql`. A failed
batch rolls back whole; rerunning any batch is safe.

## Rollback

`rollback.sql` clears the three columns of exactly the legs of that run whose
snapshot is still an archive restore and was written at or after the run
time. By hand:

```sql
UPDATE journey_legs SET final_train_uid = NULL, final_snapshot = NULL, final_snapshot_at = NULL
WHERE final_snapshot->>'source' = 'archive' AND final_snapshot_at >= '<run time>';
```

The sweep does not rewrite an archive snapshot: it only copies from a live
`trains` row, and a leg with no subscription has its copy cleared
(`clear_orphan_snapshots`), as for any snapshot.
